# X83C 脱敏抓包与实机验证报告

更新时间：2026-08-18

## 范围与隐私

本报告来自一台旧款 352 X83C。抓包点位于可观察流量的隔离局域网，测试均为
本地、单一、可逆动作。主动作记录包含 208 个数据包，
抓包程序报告内核丢包为 0。

公开版不包含原始 pcap、证书、解密日志、真实 IP/MAC、绝对时间或完整设备云
消息。下文的 `<DEVICE_MAC>`、`<DEVICE_IP>` 和 `<SEQ>` 都是占位符；命令中的
协议常量、状态偏移和响应延迟予以保留，因为它们是实现本地兼容所需的证据。

## 验证资料组成

本地证据按用途分为：

1. 设备静置时的被动基线与周期状态广播。
2. 物理按键依次切换屏幕、风量、自动、睡眠、极速和电源的相对时间线。
3. 屏幕、电源、1–6 档风量、模式、童锁和定时的单动作请求/响应记录。
4. 只读 `0x23` 发现请求及两份相同响应。
5. 故意构造的错误长度帧，以及模式值 `04`、`05` 的否定实验。
6. 设备启动后的旧云端 TLS 握手与受控证书替换实验。

一轮早期全设置测试把两字节 outer sequence 错写成一字节，生成 22 字节畸形
请求；设备全部忽略。该轮仅作为负面样本，不参与任何“支持”结论。后续使用
单一 UDP socket、正确两字节序列号的测试重新验证了全部设置。

## 本地 UDP 外层与确认机制

设备使用 UDP `11530`。X83C 的正常查询/控制请求为 23 字节：

```text
A1 04 <DEVICE_MAC:6> 0E 00 <SEQ:2>
<COMPANY> 02 <AUTH:2> 01 A5 A0 <CMD> <VALUE> 00 <CHECKSUM>
```

`company` 和 `auth` 必须从设备响应学习。测试设备通告并要求的 auth 为
`04 03`；旧集成固定发送 X83 常见的 `05 04`，是“能读取、不能控制”的原因
之一。另一个原因是旧实现遗漏了 X83C 控制命令末尾的内层加和校验。

普通控制命令的 `CHECKSUM` 是此前五个内层字节
`A5 A0 CMD VALUE 00` 之和的低 8 位。状态查询
`A5 A0 11 11 00 00` 是已经抓包确认的固定例外。

设备响应会回显请求的两字节 outer sequence。同一动作常收到两份等价响应；
实现应接受第一份校验通过且序列匹配的状态，再忽略重复包。单动作样本的首份
确认延迟约为 236–686 ms，因此控制不能只按“UDP 已发送”立即宣告成功。

## 模式的实机边界

状态低半字节的实机含义为：1 自动、2 睡眠、3 极速、4 手动。手动不是一个
可直接设置的模式命令，而是发送 1–6 档风量后由设备进入的状态。

APK 的 X83 构造器还存在 `51 05`“极净”，但测试 X83C 对 `51 05` 没有状态
变化；受控测试的 `51 04` 同样被忽略。极速则会持续运行，并不是达到 PM 阈值
或经过一段时间后自动退出的“极净”。因此集成在 X83C 上不暴露极净，也不把
手动伪装成可发送的 `mode=4`；同族其他型号是否接受 `05` 仍标为实验性。

## 状态数据报与字段

普通 X83C 状态 UDP 数据报为 49 字节：16 字节 outer header 加 33 字节
payload。模式切换时还观察到 81 字节数据报，其 payload 为一个 route 字节后
连续两个 32 字节状态记录；最后一条才是当前状态。解析器不能假定每个合法状态
永远只有一条记录。

下表是普通 49 字节 UDP 数据报的零基偏移；外层身份字段已从公开示例中移除：

| UDP 偏移 | 含义 | 实机/解析器范围 |
|---:|---|---|
| 19 | 高半字节滤芯风量配置；低半字节模式 | 配置 2；模式 1–4 |
| 20 | 风量档位 | 1–6 |
| 21 | 关机定时选择 | `00/01/02/03/05/08` |
| 22 | 空气质量代码 | 实机见 1；APK 解析 1–3 |
| 23 | 童锁 | `00` 关，`11` 开 |
| 24 | 屏幕 | `00` 开，`11` 关 |
| 25 | 电源 | `00` 开，`11` 关 |
| 26–27 | 定时剩余 | 大端分钟 |
| 28–29 | PM2.5 | 大端整数，µg/m³ |
| 35–36 | `onlineTotal` 原始字段 | 语义未确认，只保留诊断值 |
| 37–39 | 本次开机处理空气量 | 十进制指数 + 大端基数 |
| 40–42 | 寿命累计净化空气量 | 十进制指数 + 大端基数 |
| 43 | linkage | APK 命名为未联动/已联动 |

空气量按 `base × 10^exponent` 解码。旧 App 代码只显式处理指数 0–3，但实机
寿命累计字段使用指数 4；它在断电后保持，并符合多年每天运行数小时的量级。
本次处理空气量从每次开机后重新增长。`filterType` 高半字节只选择档位对应的
CADR/风量曲线，不代表“滤芯已安装”、原厂认证或滤芯剩余寿命。

## 只读发现

定向发现请求使用 outer `A1 04`、设备 MAC、目标 wire type 和 payload `23`。
测试设备返回两份相同的 27 字节响应，响应包含设备 IP 和 MAC；开机时也会
周期广播以 `A1 06` 开头的 27 字节发现信息。常规 49/81 字节状态使用
`A1 04`，两者不能只凭首字节混为一类。

旧 App 在某些发现结果后会继续发送 `0x24` 锁定命令。该行为会改变设备状态，
不属于发现；HA 自动发现只实现 `0x23` 读取，不复刻 `0x24`。

## 旧云连接的抓包观察

设备重启后会先做公网连通性检查，再连接 `wifi.352air.com:11571` 获取工作
服务信息，随后建立 `*.yunext.com` 体系下的长连接。测试环境包含本地代理与
地址映射，因此这些目标地址不能视作稳定协议事实，本报告不发布抓到的地址。

两段连接都协商 SSL 3.0，最终使用 `TLS_RSA_WITH_RC4_128_SHA`；客户端只提供
RC4-SHA、RC4-MD5 和 3DES-SHA 这组三种旧套件。工作连接接受了 2021 年已经
过期、且主机名不匹配的 `*.yunext.com` 证书；隔离网络中的受控实验还确认，
它会继续接受替换的自签名工作服务器证书并交换应用数据。

这与 APK 中空实现的证书链校验逻辑相互印证，说明旧设备云链路不具备现代 TLS
身份保证。本项目不会实现或依赖该云链路，也不发布代理代码、私钥、证书、明文
日志或可用于第三方设备的原始会话数据。

## 对集成实现的结论

- 外层 `company/type/auth` 从设备响应学习，不能硬编码另一型号的头字段。
- X83C 控制必须带 A5A0 内层加和校验，并等待序列匹配的确认状态。
- 重复响应应去重；畸形长度、身份不匹配、校验失败和未知枚举不能更新状态。
- X83C 只声明已验证的自动、睡眠、极速和“风量进入手动”；极净不在实机支持表。
- 49/81 字节两种状态形态都要正确提取最后一条记录。
- 原始抓包只保存在研究者本地，公开问题和 PR 应继续使用占位符与相对时间。
