# 352Air 3.2.16 APK 静态分析

更新时间：2026-08-17

## 结论摘要

这版 352Air 同时实现了云端长连接和局域网 UDP 控制。只要设备已经连上 Wi-Fi、HA 与设备位于可互通的局域网，核心状态读取和控制并不依赖仍可登录的 352 账号。

X83/X83C 使用短 `A5 A0` 协议；X50/X50S/X60/X70 与 G30/G45 使用带 CRC16 的 `F0 72` 长协议；M25 是空气检测仪，使用另一套 `FA/E5` 短协议，在 APK 中可确认的本地可设置项只有背光。不能按外层 `deviceType` 单独可靠区分同协议族里的全部零售型号，因此 HA 自动发现应先识别协议族，再让用户确认或手动覆盖具体型号。

本文只记录静态代码能够证明的事实。没有安装或运行 APK，没有登录账号，没有向设备发送数据，也没有操作 HA。X83C 的少量项目内抓包结论单独标为“实机已验证”；其他型号均不能因为 APK 中存在代码就宣称已经过实机验证。

## 配网流程

### 用户界面支持的型号

“添加设备”界面直接提供五种选择：

| UI 型号 | pointType | 外层 deviceType / wire type |
|---|---:|---:|
| M25 | 1 | 1 |
| X83 | 2 | 2 |
| G30 | 3 | 4 |
| X83C | 4 | 2 |
| X50 | 5 | 3 |

APK 还认识 X50S（pointType 6/type 3）、X83C Plus（7/type 2）、X60（8/type 3）、X70（9/type 3）和 G45（10/type 4），但它们没有作为这版添加页的独立入口出现，通常来自服务器设备元数据或历史绑定记录。

### 同时运行两套 SmartConfig

点击开始后，`AddDeviceConnectActivity` 会同时启动 EasyJoin 和 Hiflying SmartLink，不是二选一。

Hiflying 分支：

- v7 数据为 `[ssidLen, passwordLen, pmkLen, extraLen] + SSID + password + PMK + extra`，按偶数长度补齐。
- PMK 使用 `PBKDF2WithHmacSHA1(password, SSID bytes, 4096, 256 bit)`。
- v7 用目的组播地址和 UDP 包长编码数据，目的端口 `6000`。
- 组播地址形如 `239.46.x.y`；分隔包使用 `239.48.0.0`，长度 30。
- 同时保留老 v3 广播编码：向子网广播 UDP `49999`，通过数据报长度传递校准、密码字符和开始/结束标记。
- 监听 UDP `49999`，总超时约 60 秒；同时每秒向 UDP `48899` 广播文本 `smartlinkfind`。
- 返回文本以 `smart_config` 开头，后续值被当作设备 MAC/标识，数据报源地址被当作设备 IP。

EasyJoin 分支：

- 向子网广播 UDP `8888`，并用 `228.x.y.z:8888` 目的组播地址编码 SSID、密码、CRC 和随机 XOR 掩码。
- 另有基于广播数据报长度的兼容编码。
- 监听 UDP `8801`，返回格式为 `A0 B0 + MAC(6) + checksum(1)`。
- 校验字节是 MAC 六字节之和的低 8 位；该分支只得到 MAC，不直接得到 IP。
- 总超时约 90 秒。

安全含义：两套老式配网都不是现代加密握手。SSID/密码虽然不是作为普通明文字符串直接广播，但编码是可逆的；同一无线网络附近的被动监听者有机会还原凭据。

### 配网完成后的设备发现

任意一套 SmartConfig 成功后，APP 会：

1. 把 SSID 和 Wi-Fi 密码以明文写入本地 greenDAO `WIFI` 表。
2. 按选定型号的 MAC 与 wire type 启动定向 UDP 发现。
3. 每约 300 ms 重试，使用三轮/每轮多次的查找参数。
4. 从返回包学习设备 IP、MAC、company、deviceType 和 auth code。

## 局域网外层协议

### 通用封装

设备 UDP 目标端口为 `11530`。外层数据包结构为：

```text
offset  size  meaning
0       1     0xA1
1       1     flags / outer command
2       6     target MAC
8       1     length = payload_length + 7
9       1     0x00
10      2     outer sequence, big-endian
12      1     company
13      1     deviceType / wire type
14      2     auth code
16      N     routed payload
```

因此外层总长为 `16 + payload_length`。`length` 是单字节，不是双字节。

局域网发现请求为：

```text
A1 04 <MAC:6> 08 00 <SEQ:2> F1 <WIRE_TYPE> <APP_AUTH:2> 23
```

发现返回的有效载荷至少包含：

```text
23 <IPv4:4> <MAC:6>
```

### company/auth 的正确处理

APP 的状态响应头解析器会从每个响应重新读取并保存：

- MAC：外层 2..7
- company：外层 12
- deviceType：外层 13
- auth code：外层 14..15

配网发现时请求可以用 APP 自己的 `F1` 与 app auth；后续状态查询和控制应使用设备响应中学到的 company/type/auth，不能把某台设备的 auth、MAC 或 company 写死到公共代码。自动发现的合理流程是“发送族探测请求 → 接受响应 → 学习头字段 → 用学习值构造后续包”。

APP 收到部分响应后还可能自动发送一个锁定类命令。HA 集成不应照搬这种隐式写操作；发现和轮询必须保持只读。

## X83 / X83C 短协议

### 内层帧和校验

查询帧固定为：

```text
A5 A0 11 11 00 00
```

控制帧为：

```text
A5 A0 <CMD> <VALUE> 00 <CHECKSUM>
```

`CHECKSUM = sum(first 5 bytes) & 0xFF`。wire type 2 的路由前缀是 `01`，所以送入外层封装的 payload 是：

```text
01 A5 A0 <CMD> <VALUE> 00 <CHECKSUM>
```

实机接收方向使用不同的状态头：X83C 状态 payload 以 `02 5A A1`
开头，外层 operation 为 `04`。普通状态 payload 长 33 字节；另观察到
一个 65 字节的模式切换帧，其结构是一个 route 字节后连续两个 32 字节
状态记录，最后一条是当前状态。查询/控制请求的 `01 A5 A0` 不能用于
识别状态响应。

### 动作表

| 动作 | cmd | APK 发出的 value |
|---|---:|---|
| 模式 | `51` | `01` 自动、`02` 睡眠、`03` 极速、`05` 极净 |
| 风档 | `52` | `01`..`06` |
| PTC | `53` | `00`, `01`, `02`；数组末尾另有 UI 哨兵 `00` |
| 关机定时 | `54` | `00`, `01`, `02`, `03`, `05`, `08` 小时 |
| 童锁 | `55` | `00`, `11` |
| 屏幕灯 | `56` | `00`, `11` |
| 滤芯位置/操作 | `57` | `01`, `02`, `03`；数组末尾另有 `00` |
| 电源 | `5E` | `35`, `11` |

这里的模式标签不能仅从数值顺序猜。X83C 实机已经确认：自动模式状态低半字节为 1，手动模式为 4；APK 的模式控制数组则是 1/2/3/5，这说明“命令值”和“状态枚举”不一定相同。

### X83C 已验证的状态字段

以下 offset 从 `A5...` 内层开头计数；外层位置等于 `16 + 1(route) + inner_offset`：

| 内层 offset | 含义 | 已验证/静态含义 |
|---:|---|---|
| 3 | 模式/滤芯打包字节 | X83C manual 状态低半字节 `4` |
| 4 | 风档 | 1..6 |
| 5 | 定时选择 | 0/1/2/3/5/8 小时 |
| 6 | 空气质量等级 | 只确认数值 1/2/3；中文语义未知 |
| 7 | 童锁 | `00` 关，`11` 开 |
| 8 | 屏幕灯 | `00` 开，`11` 关 |
| 9 | 电源 | `00` 开，`11` 关 |
| 10..11 | 剩余定时 | 大端分钟 |
| 12..13 | PM2.5 | 大端整数 |
| 21 + 22..23 | 本次累计空气量 | 十进制指数 + 大端基数 |
| 24 + 25..26 | 寿命累计净化空气量 | 十进制指数 + 大端基数 |

状态 offset 3 的高半字节在 APK 中叫 `filterType`，但它不是“已安装滤芯”
或滤芯寿命。设备列表用这个值选择档位对应的 CADR/风量显示曲线：

| X83 系列配置码 | 1..6 档显示风量（m³/h） |
|---:|---|
| 0 | 140 / 240 / 360 / 500 / 610 / 760 |
| 1 | 60 / 140 / 220 / 330 / 390 / 500 |
| 2 | 130 / 220 / 330 / 430 / 500 / 640 |

实测 X83C 一直上报配置码 2。APK 没有为三套 X83 曲线提供可靠的零售
滤芯名称，因此 HA 显示“配置 0/1/2”，并把对应档位风量放入实体属性。
旧 App 的“中效空气过滤器 / 高效异味过滤器 / 超细颗粒过滤器”是三个
滤芯仓位；寿命记录依赖滤芯 SN 和云端数据，不在这个状态半字节中。

空气质量 1/2/3 的确切中文枚举没有在可达 UI/解析代码中找到。HA 集成
为了可读性按等级顺序展示为“优/良/差”并保留 `raw_code`，但该文字映射
属于展示层推断，不是 APK 静态确认结论。

旧 App 的计算分支只显式覆盖指数 0..3，但 X83C 实机寿命累计量使用了
指数 4。结合跨开机保持、约 270 万 m³ 的实际读数和多年每天数小时的
运行量级，本项目把该格式按 `base × 10^exponent` 解码并接受 0..4；
更高指数保留为原始诊断值，不发布为传感器数值。

## X50 / X50S / X60 / X70 长协议

### 完整内层构造

四个型号在 APK 中共用 wire type 3、X50 页面和同一个命令构造器。单值控制内层固定 15 字节：

```text
F0 72 00 0D
03 04 02
<INNER_SEQ_HI> <INNER_SEQ_LO>
03 <CMD> <VALUE> 00
<CRC_HI> <CRC_LO>
```

- `00 0D` 是 `inner_length - 2`，即 13。
- CRC 输入为内层 offset 2..12，共 11 字节。
- CRC 是 CRC-16/GENIBUS：poly `0x1021`、init `0xFFFF`、xorout `0xFFFF`，高字节在前。
- wire type 3 的路由前缀是 `01`，所以外层 payload 为 `01 + 上述 15 字节`。
- 该控制包的外层 `length` 因而是 `16 + 7 = 23 (0x17)`，外层总长 32 字节。

查询状态使用同一构造器，`cmd=11, value=11`。

X50 页面同样用 `filterType` 选择风量曲线：配置 0 为
150/220/300/400/510/600 m³/h，配置 1 为 120/170/240/330/430/540 m³/h。
解析器还接受配置码 2，但 APK 没有为它提供风量表或可靠名称，故只保留配置码。

### 四型号共同的动作表

| 动作 | cmd | value |
|---|---:|---|
| 查询状态 | `11` | `11` |
| 模式 | `51` | `01` 自动、`02` 睡眠、`03` 极速、`05` 极净 |
| 离散风档 | `52` | `01` 小卧室、`02` 大卧室、`03` 客厅、`04` 办公室、`05` 极速；UI 数组末尾有 `00` 哨兵/停止项 |
| PTC | `53` | `00`, `01`, `02` |
| 关机定时 | `54` | `00`, `01`, `02`, `03`, `05`, `08` 小时 |
| 童锁 | `55` | `00` 开，`11` 关 |
| 屏幕灯 | `56` | `00` 开，`11` 关 |
| 电源 | `5E` | `00` 开，`11` 关 |

APK 没有给 X50S、X60、X70 建立另一套 cmd/value 表；可证明的是它们共享上述 wire type 和控制页面。不能进一步声称所有硬件功能都完全相同。X50S 页面存在额外滤芯展示逻辑，但没有由此得到一套独立的基础控制命令。

论坛“X50 可读取但控制失败”的现象与静态代码不矛盾：存在控制构造代码只证明 APP 会生成这些帧，不证明所有固件接受它们。未经对应真机验证的 HA 控制必须标实验性，并保留只读回退。

## G30 / G45 长协议

G30/G45 使用相同的 `F0 72` 结构，内层 byte 4 和外层 deviceType 为 4，路由前缀仍是 `01`。

### 动作表

| 动作 | cmd | value |
|---|---:|---|
| 查询状态 | `11` | `11` |
| 模式 | `51` | UI 明确提供 `01` 自动和 `05` 极净；解析器接受 1..5，但 G30 页面没有证明 2/3/4 可作为控制选项 |
| PTC | `53` | `00`, `01`, `02` |
| 关机定时 | `54` | `00`, `01`, `02`, `03`, `05`, `08` 小时 |
| 童锁 | `55` | `00` 开，`11` 关 |
| 屏幕灯 | `56` | `00` 开，`11` 关 |
| 连续风量 | `58` | 两字节大端 m³/h，见下表 |
| 电源 | `5E` | `00` 开，`11` 关 |

连续风量使用变体内层：

```text
F0 72 00 0D 04 04 02 <SEQ:2> 03 58 <FLOW_HI> <FLOW_LO> <CRC:2>
```

范围来自 APK 滑块的精确换算：

| 型号 | UI progress | 风量值 | 步进 |
|---|---:|---:|---:|
| G30 | 0..52 | 40..300 m³/h | 5 |
| G45 | 0..82 | 40..450 m³/h | 5 |

G45 判据是设备当前 MCU 版本字符串包含 `G45`。

APK 没有 Home Assistant 百分比概念，只保存并显示 m³/h。因此不存在“APK 原生的精确百分比映射”。如果 HA 需要 0..100%，建议作为集成层设计选择使用：

```text
percent = round((flow - 40) * 100 / (max_flow - 40))
flow = round_to_step_5(40 + percent * (max_flow - 40) / 100)
```

并把 0% 留给关机，而不是伪装成 40 m³/h。这是 HA 设计建议，不是 APK 协议事实。

### G30/G45 状态字段

通过长帧 CRC 后，APP 从状态数据区读取：

- offset 3：模式/滤芯打包字节
- offset 5：定时选择
- offset 6：空气质量等级
- offset 7：童锁
- offset 8：屏幕灯
- offset 9：电源
- offset 10..11：剩余定时
- offset 12..13：PM2.5
- offset 14：温度
- offset 15：湿度
- offset 16..17：CO₂
- offset 18：PTC
- offset 27..28：连续风量，大端 m³/h

G30 解析器明确把滤芯配置高半字节 `0` 记作“标准款”，非零记作“超级碳”。
这仍是风量/滤芯配置，不是滤芯寿命或安装真实性状态。

这些 offset 从解析器取出的状态数据区起点计，不是从 UDP 包头起点计。

## M25 `FA/E5` 协议

M25 在这版 APP 中是 PM2.5 检测仪页面。它轮询检测值、查询背光和 MCU 信息，没有净化器的电源、风档、模式、童锁或定时 UI。

wire type 1 的路由前缀为 `03`，目标 UDP 端口仍为 `11530`。

### 已确认的本地动作

| 动作 | 内层帧 | 说明 |
|---|---|---|
| 查询检测状态 | `FA A0 11 11 00 00` | 固定 6 字节 |
| 查询背光 | `FA A4 02 01 A1` | 最后一字节是前四字节和的低 8 位 |
| 设置背光 0 | `FA A3 03 01 00 A1` | APP 文案为“5 分钟关背光”；路由前缀另加 `03` |
| 设置背光 1 | `FA A3 03 01 01 A2` | APP 文案为“常亮”；路由前缀另加 `03` |

以设置背光 1 为例，外层 payload 为：

```text
03 FA A3 03 01 01 A2
```

再按通用 `A1` 外层包裹；company/type/auth 必须从该设备响应学习，不能写死。payload 长 7，所以外层 length 为 `0E`，外层总长 23。

状态响应解析器可确认：

- `03 E5 A1/A2 ...` 形态、总长 17 的响应包含 PM 值及 linkage 状态。
- `03 E5 A3 03 01 <backlight> ...` 或 `03 E5 A4 ... <backlight> ...` 返回背光状态。

`linkage` 不是账号绑定或网络在线标志。APP 将值 `1` 解释为已联动，并另外保存
`linkageMac`；联动设置页面还为所选设备保存上下限阈值和对应风速。因此集成把
`0/1` 显示为“未联动/已联动”，同时在实体属性中保留 `raw_code`。其他值仍视为未知。

M25 的“完整净化器控制表”不存在；将 X83/X50 命令套用到它属于无证据猜测。

## 响应校验与长帧识别

长协议解析器接受设备协议类型字节 `84`（响应）或 `03`，后续子类型为 `02`，然后对状态帧主体做 CRC16/GENIBUS 校验。控制实现应同时校验：

- 外层 MAC 与预期设备一致。
- 外层 company/type/auth 已学习且持续更新。
- outer sequence 与 inner sequence 的响应关系。
- 长帧声明长度与实际长度。
- CRC 正确后才更新状态。

X83 短状态帧没有同样的 CRC16，应按固定头、最短长度、MAC 和序列做更严格的边界校验。

## 自动发现与手动配置建议

可靠的 HA 配置流程应分两层：

1. 在 UDP `11530` 上进行只读发现，收集源 IP、MAC、company、wire type 和 auth。
2. 按 wire type 做只读状态查询，验证协议族与响应校验。
3. 如果只能确定族而不能确定 exact 型号，显示候选列表而不是自动猜型号。
4. 用户确认后才创建控制实体；未验证型号默认只读或显著标记“实验性控制”。

推荐的自动识别边界：

- type 1 → M25 族，背光/检测协议。
- type 2 → X83/X83C/X83C Plus 族；纯本地协议不足以稳定区分 exact 型号。
- type 3 → X50/X50S/X60/X70 族；纯本地协议不足以稳定区分 exact 型号。
- type 4 + MCU 字符串含 `G45` → G45，否则暂列 G30/unknown type-4。

手动模式至少应允许填写 IP/主机名、MAC、型号；company/auth 默认仍优先从只读响应学习，只在高级故障排查时允许手工覆盖。IP 不能当稳定唯一标识，DHCP 改址后应按 MAC 重新发现。

## 云端通信

APP 的设备控制发送器会根据连接状态选择路径：设备云在线时走 TCP 长连接，本地可达时走 UDP。因此“APP 有云服务器”与“局域网可直接控制”同时成立。

云端大致流程：

- 先连接 `352.yunext.com` 的负载均衡端口 `11591`。
- 发送服务发现命令，响应给出实际 TCP 地址与端口。
- 再建立设备云长连接，发送登录/加入命令，订阅设备状态，并约每 5 秒心跳。
- HTTP API 另走 `https://352.yunext.com` 的 Retrofit/OkHttp 请求，用于登录、设备列表、分享、历史数据、固件元数据等。

静态代码中的 TCP TLS 信任管理器不执行证书链校验，也没有发现主机名校验；随 APK 打包的证书流被打开但没有用于实际校验。本项目既有网络观察还显示老云端协商极旧的 SSLv3/RC4 套件并返回过期、主机名不匹配的证书。后者是网络实测，不是仅凭 APK 得出的结论。

这意味着旧 APP 的设备云通道具有很高的中间人风险，不适合为了恢复功能而长期暴露在不可信网络中。局域网 HA 控制不需要复刻这条不安全云链路。

## 账号与本地存储

静态确认的账号处理包括：

- 登录密码先做大写十六进制 MD5。
- 请求参数还使用 APK 内嵌私钥做 RSA/SHA1 签名；私钥随客户端分发，不能提供真正的服务端身份保证。
- SharedPreferences 中保存 token，也保存原始密码字段。
- greenDAO 数据库名为 `ac_db`，Wi-Fi 表保存 SSID 和密码。
- Device、PM 历史、分享信息等也保存在本地数据库/偏好中。
- 调试日志路径会打印网络包和部分运行信息；外部日志写文件的代码存在，但未确认正常流程一定调用。

`android:allowBackup=false` 降低普通 ADB 备份暴露，但不能弥补明文凭据、老 Android 设备、root 或恶意本地组件带来的风险。

## 更新与 WebView 风险

APP 的更新服务可以从 Intent 中取得 APK URL，交给系统 DownloadManager 下载，完成后启动包安装界面。静态代码中未看到应用层的下载域名白名单、文件哈希或签名预校验。Android 最终安装通常仍要求系统/用户确认，但这是明显的老式更新设计。

部分设备固件升级 URL 使用明文 HTTP 并被发送给 Wi-Fi 模组；APP 本身未验证固件哈希或签名。模组固件内部是否还有独立验签未知。

内置 WebView 开启 JavaScript、文件访问和混合内容兼容。未发现自定义 JavaScript bridge；相关 URL Activity 看起来不是对外导出的，因此风险低于任意外部应用直接注入 URL，但来自服务端或跳转链的内容仍需谨慎。

Manifest 还包含较宽的旧式存储、位置、网络和设备权限，以及多个第三方推送/统计 SDK。若只是为了 HA 局域网接入，不建议重新登录或日常使用这版 APK。

## 无法从 APK 单独确认的事项

- 2019 年账号现在无法登录的确切服务端原因。
- X83 空气质量数值 1/2/3 的官方中文语义。
- X83 与 X83C/X83C Plus 的纯本地稳定型号判据。
- X50、X50S、X60、X70 的纯本地稳定型号判据及所有硬件功能差异。
- X50 系列各固件是否实际接受 APK 生成的控制帧。
- G30 解析器接受的模式 2/3/4 的控制语义。
- M25 不同 company 固件是否存在另一种查询变体，以及除背光外是否有未暴露的可设置功能。
- 设备固件自身是否验证 HTTP 下载的固件签名。

这些项目都需要对应型号真机的只读抓包、可逆动作验证或固件样本；静态相似性不够。

## 对 HA 实现的直接要求

- 公共仓库不得包含真实 MAC、内网 IP、HA token、Wi-Fi 凭据、抓包或 APK。
- 发现阶段只发查询，不自动锁定、不改变任何设备状态。
- 从响应学习 company/auth，不写死用户设备字段。
- 每个协议族单独实现编解码器，不通过“型号名字相近”复用控制。
- X50/X50S/X60/X70、G30/G45 和 M25 在无真机验收前均标实验性。
- 提供“自动发现 + 型号确认”和“手动 IP/MAC/型号”两条配置路径。
- 控制后等待匹配序列且校验正确的状态响应；超时应回滚 UI 乐观状态并保留只读实体。
- 对未知枚举保留原始数值传感器，不擅自添加语义标签。
