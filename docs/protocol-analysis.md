# 本地协议分析与实现边界

## 起因

老款 352Air App 的账号服务已经无法作为可靠入口，但设备局域网功能仍在
运行。分析目标不是恢复或仿冒云服务，而是确认用户自己的设备能否在不
联网的情况下继续使用。

证据来自三类独立来源：旧 Android App 的静态构造器/解析器、脱敏局域网
流量，以及一台 2019 年 X83C 的可逆动作验证。没有把 APK、真实抓包、
MAC、IP、token 或证书加入公开仓库。

## 外层协议

设备使用 UDP 11530。数据报以 `A1` 开头，包含目标 MAC、两字节序列号、
company、wire type、两字节 auth 和路由后的内层负载。长度字段等于内层
负载长度加 7。

设备响应会返回自己的 company/type/auth。X83C 不能沿用 X83 的固定鉴权
码；早期接入控制失败的主要原因正是使用了错误 auth，同时遗漏了 X83C
控制帧需要的内层加和校验。本实现始终从设备响应学习这些字段。

只读发现使用外层命令 `0x23`。旧 App 在部分发现结果后还会发 `0x24`
锁定操作，本项目明确不实现这个副作用。

## 四个协议族

| wire type | 设备族 | 内层协议 |
|---:|---|---|
| 1 | M25 | FA/E5 短帧 |
| 2 | X83/X83C/X83C Plus | A5A0 短帧和加和校验 |
| 3 | X50/X50S/X60/X70 | F072 长帧和 CRC-16/GENIBUS |
| 4 | G30/G45 | F072 长帧、连续风量和 CRC-16/GENIBUS |

wire type 只能可靠识别设备族，不能区分同族全部零售型号。G45 可根据
MCU 版本字符串包含 `G45` 做 best-effort 判断；其他情况由用户确认型号。

## X83C 真机结论

- 发送查询/控制使用 route `01` 和 `A5 A0`，接收状态却以
  `02 5A A1` 开头；两者不能混用。
- 普通状态 payload 为 33 字节。模式切换时还观察到一个 65 字节
  payload：一个 route 字节后连续两个 32 字节记录，应采用最后一条。
- 模式状态：1 自动、2 睡眠、3 极速、4 手动。
- 风量命令 1..6 会进入手动模式。
- 测试设备忽略模式命令值 4 和 5，因此不能把 5 当成可用“极净”。
- 极速是持续模式，不是极净的临时状态。
- 童锁、屏幕、电源和 0/1/2/3/5/8 小时关机定时已验证。
- PM2.5、剩余分钟和累计空气量来自本机状态包。
- 空气量使用十进制指数加两字节基数。旧 App 只显式处理指数 0..3，
  但 X83C 实机的寿命累计净化量使用指数 4；本项目按实机证据支持 0..4。
- “累计空气量”会随本次开机运行增长；“累计净化空气量”是跨开机保存的
  寿命累计值。测试设备约 270 万 m³，与多年每天数小时运行的量级相符。
- 滤芯打包半字节只能证明类型/位置状态，不能证明“已安装原厂且未到期”。
- `linkage` 值 `0/1` 在 APK 中对应未联动/已联动，并与 `linkageMac`、
  联动阈值和联动风速设置配套；它不是账号绑定或网络在线状态。

空气质量字段接受 1/2/3，但 APK 中没有找到官方中文枚举。HA 展示层按
等级顺序映射为“优/良/差”，同时保留 `raw_code`；这是明确标注的展示
推断，不冒充旧 App 中已找到的官方文案。

## 未实机设备

X50 系列和 G30/G45 的帧结构、CRC 与命令表可以从 APK 静态确认，但存在
固件是否接受本地控制的不确定性，所以默认明确标记实验性。M25 是检测
仪，只确认状态与背光协议，不套用净化器命令。

## 安全原则

- 只实现局域网读取和设备控制，不连接旧云端。
- 自动发现不写入设备状态。
- 对长度、MAC、序列号和协议族完成边界校验；存在 checksum/CRC 的帧还要
  通过对应校验后才更新 HA。
- 控制必须收到确认状态；超时不保留错误的乐观 UI。
- 未知枚举保持 raw，不根据相邻型号猜测。

更完整的设备族、帧构造、解析器、配网和旧 App 安全分析见
[APK 静态分析报告](apk-static-analysis.md)。
